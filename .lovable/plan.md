# NAZRA — خطة التنفيذ المستمدة من الملفين المرجعيين

المرجعان (`NAZRA_LOVABLE_MASTER_EXECUTION_BRIEF_001` و`NAZRA_MASTER_EXECUTION_BRIEF 2.1`) وثائق سياق وحوكمة، وليست تفويضًا بالتعديل. الخطة التالية تلتزم بذلك: لا توسيع نطاق، لا فتح F2، لا مساس بـSmart Freeze، ولا ادعاء Certification.

## الحالة الحالية (من `roadmap.md` داخل المشروع)

- F1 مغلق (37/37) — PASS مقبول، غير مُعتمَد كشهادة.
- Unit A (سلطة الإشعارات عبر RPC مشتق الـtenant) — منفّذ مع أدلة.
- Unit B (عقد بيانات لوحة التحكم `paid_amount`) — منفّذ مع أدلة.
- المتبقي المفتوح: التحقق المستقل ثم البوابة البشرية.
- مخاطر مفتوحة: RISK-007، RISK-008، PRE-EXT-001. PRE-TS-001: مُحتوى.

بحسب «الإجراء التالي القانوني» في الملف 2.1، الخطوة رقم 6 هي التحقق المستقل من Unit A/B — وهي بالضبط البند المفتوح الوحيد في خارطة الطريق الحالية.

## المرحلة 0 — اعتماد المرجع وتسوية التعارضات (توثيق فقط)

1. إنشاء `docs/governance/MASTER_EXECUTION_BRIEF_ADOPTION.md` يسجّل:
   - ترتيب سُلطة المصادر (قرار بشري مجمّد ← عقد نطاق ← دليل حديث ← تدقيق ← دليل تشغيلي ← سرد قديم).
   - تسوية التعارضين الصريحين دون إخفاء أي رقم:
     - 37/37 مقابل 11/37 — تُسجَّل كتعريفين مختلفين (إجمالي الحواف المُحاسَبة مقابل العناصر القابلة للتنفيذ وقت التجميد).
     - 155 مقابل 118 — مقياسان تاريخيان منفصلان، لا تُكتب عبارة «155 صار 118» بدون تعريف مقياس موحّد.
   - فروق اللقطات (1,933 ملف في التدقيق مقابل 1,226 في R1) كلقطتين منفصلتين.
2. تسجيل سجل المقاييس (Metric Registry) بالتعريف + الأمر + الطابع الزمني لكل مقياس سيُستخدم لاحقًا.
3. لا تعديل مصدر، لا migration، لا grants.

**المخرج:** وثيقة اعتماد + سجل مقاييس. **البوابة:** مراجعة بشرية.

## المرحلة 1 — التحقق المستقل من POSTF1 (تحقق فقط، صفر تعديل مصدر)

نطاق ثابت: الملفات الخمسة الواردة في `postf1-scope-001-manifest.json` فقط.

- إعادة إنتاج هاش البيان والتأكد من عدم انحراف النطاق.
- إثبات V1–V8 حيًّا:
  - V1/V2: إنشاء إشعار مُصرَّح به يُحفظ ويُقرأ من الجرس/الصفحة.
  - V3: هدف داخل نفس الـtenant لكنه غير عضو ← رفض 403/42501 بلا صف.
  - V4: هدف من tenant آخر ← رفض بلا صف.
  - V5: INSERT مباشر من العميل ← رفض على مستوى الصلاحيات.
  - V6: استدعاء `anon` للـRPC ← رفض.
  - V7/V8: عرض `paid_amount` في الفواتير الأخيرة بلا أي أثر لـ`amount_paid`، ولوحة التحكم بلا أخطاء وقت التشغيل.
- فحوص الجودة: typecheck، build، fitness، Vitest، ومقاييس الطبقات دون تغيير.
- إثبات سلبي: لا مساس بـF2 ولا RLS/migrations/tenant/permissions/finance/domain.

**المخرج:** `docs/governance/POSTF1_VERIFICATION_RECORD.md` + دليل JSON. **الحكم:** PASS / FAIL / BLOCKED فقط — لا Certification.

## القواعد الحاكمة طوال الخطة

- IMPLEMENTED ≠ VERIFIED ≠ CERTIFIED؛ الوكيل لا يمنح شهادة لنفسه.
- F2 يبقى غير مُصرَّح به، وSmart Freeze نشط (الدفاتر، الدفعات، حركة المخزون، المزامنة، سلطة الـtenant، الصلاحيات، RLS، الترحيلات).
- لا إعادة كتابة، لا microservices، لا CQRS/Event Sourcing عام، لا مطاردة «صفر مخالفات».
- التوقف الفوري عند أي انحراف نطاق أو حاجة لسطح جديد غير معتمد، مع تقرير توقف بدل الارتجال.
- المخاطر المفتوحة RISK-007 / RISK-008 / PRE-EXT-001 تبقى مفتوحة، وPRE-TS-001 يُسجَّل كـDELTA محتوى عند كل تكرار.

## تفاصيل تقنية

- أدوات التحقق: `scripts/audits/*` و`scripts/fitness/run-all.mjs` و`scripts/audits/typecheck-app.mjs` (يتسامح مع TS7011 المملوك للمنصّة فقط).
- الأدلة الحيّة عبر استعلامات قاعدة البيانات واستدعاءات PostgREST بهوية حقيقية، وليس عبر `SET ROLE`.
- مخرجات JSON تُكتب تحت `scripts/audits/output/` وسجلات الحوكمة تحت `docs/governance/`.
