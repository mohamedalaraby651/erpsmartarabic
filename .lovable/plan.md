# OPA-TBL-001 — تطوير تجربة الجداول والفلاتر على مستوى النظام

الحالة المقترحة: **Candidate Program — غير مصرّح بالتنفيذ بعد**  
المرجع الأول: شاشة الفواتير في `OPA-UI-003` بعد قبولها بشريًا.  
الهدف: تحويل الجداول من عرض ثابت إلى مساحة عمل عربية سريعة وقابلة للتخصيص، دون تغيير قواعد الأعمال أو مصدر الحقيقة.

## 1. مبادئ النطاق والحوكمة

- الفصل الإلزامي بين:
  1. **Presentation:** الألوان، المسافات، الكثافة، العرض، الترتيب، التثبيت والاستجابة.
  2. **Interaction State:** الفلاتر، الفرز، الاختيار، الصفحة والعرض المحفوظ.
  3. **Query Behavior:** ترجمة الحالة إلى الاستعلام مع بقاء `OR` داخل العمود و`AND` بين الأعمدة.
  4. **Domain Rules:** تبقى خارج هذه المبادرة ولا تتغير.
- لا تعميم قبل قبول `OPA-UI-003` على شاشة الفواتير كمرجع.
- لا migrations أو RLS أو صلاحيات أو منطق مالي/مخزني، ولا فتح F1 أو تنفيذ F2.
- لا إعادة بناء لمعمارية الجداول أو إنشاء Query Service/Repository جديد لمجرد توحيد الواجهة.
- أي خلل تشغيلي مباشر يظهر أثناء رحلة شاشة معيّنة يُعالج في دفعتها فقط؛ الدين المعماري يسجل ولا يوسّع النطاق.
- كل شاشة تمر: **Static Trace → Runtime Proof → Evidence → Human Acceptance**.

## 2. الشكل المستهدف للمستخدم

### شريط عمل موحّد
- بحث عام واضح، زر الفلاتر، الفلاتر المحفوظة، تخصيص العرض، التصدير، والإجراء الأساسي في صف منظم.
- عدد النتائج وحالة التصفية ظاهران دون ازدحام.
- عند صغر العرض تنتقل الأدوات الثانوية إلى قائمة واحدة، مع بقاء البحث والإجراء الأساسي ظاهرين.

### رأس جدول هادئ وواضح
- خلفية محايدة وحدود خفيفة من رموز التصميم الحالية.
- عنوان العمود هو العنصر الأوضح؛ أيقونتا الفرز والتصفية أصغر ولا تتنافسان معه.
- الفلتر النشط فقط يستخدم لون النظام وشارة عدد القيم.
- الحالات تستخدم ألوانًا دلالية ثابتة: نجاح/تحذير/خطر/محايد، لا ألوان زخرفية ولا قيم hardcoded.

### إيقاع ومسافات
- شبكة 4/8px: أدوات متقاربة وظيفيًا، وفواصل 8–16px بين المجموعات.
- ارتفاعات ثابتة للأدوات والصفوف، بلا تمدد بسبب العملة أو الحالة.
- أرقام tabular ومحاذاة منطقية، وعملة/تاريخ/حالة في سطر واحد.
- لا page-level horizontal overflow؛ التمرير الأفقي داخل الجدول فقط.

## 3. القدرات الوظيفية المستهدفة

### A — فلترة احترافية موحّدة
- **نص/مرجع:** بحث حر + قيم موجودة قابلة للبحث والتحديد المتعدد.
- **حالة/تصنيف:** بحث داخل الخيارات، تحديد متعدد، تحديد/إلغاء نتائج البحث الحالية.
- **تاريخ:** اليوم، أمس، آخر 7/30 يومًا، هذا/الشهر السابق، ومن–إلى.
- **رقم/مبلغ:** يساوي، أكبر، أصغر، بين، مع تحقق من الحدود.
- دعم «فارغ/غير فارغ» فقط عندما يسمح عقد الحقل بذلك.
- الاحتفاظ بالقيم المختارة عند البحث أو تحميل دفعة جديدة من الخيارات.
- تطبيق صريح أو تلقائي حسب النوع: النص مؤجل زمنيًا، والاختيارات تُراجع قبل التطبيق.
- الفلاتر النشطة تظهر كشرائح قابلة للحذف منفردًا، مع مسح الكل وعدد النتائج.
- اتساق كامل بين الصفوف والعدد والترقيم والتصدير والاختيار الجماعي.

### B — تخصيص الأعمدة
- تغيير العرض بالسحب دون refetch أو query invalidation.
- حدود min/max، ونقر مزدوج للملاءمة الفعلية حسب الرأس والمحتوى الظاهر.
- إظهار/إخفاء، ترتيب بالسحب مع بديل أزرار/لوحة مفاتيح، واستعادة الافتراضي.
- تثبيت عمود الهوية والإجراءات اختياريًا عندما تسمح المساحة، مع RTL صحيح.
- ثلاثة مستويات كثافة وارتفاع قابل للضبط، ورأس ثابت داخل منطقة الجدول.
- مفتاح التفضيلات: `user + screen + version` حتى لا تتسرب إعدادات شاشة أو حساب إلى آخر.

### C — عروض عمل محفوظة
- العرض المحفوظ يتضمن: الفلاتر + الفرز + الأعمدة الظاهرة وترتيبها وعروضها + الكثافة + حجم الصفحة، ضمن ما تسمح به البنية الحالية.
- حفظ باسم، تطبيق، إعادة تسمية، حذف، وتحديد عرض افتراضي إن كان ذلك ممكنًا بلا schema جديد.
- إصدار configuration version مع fallback آمن عند إضافة/حذف عمود.
- تظل التفضيلات المحلية خاصة بالجهاز إذا لم تدعم البنية الحالية مزامنتها؛ لا ندّعي مزامنة بين الأجهزة دون دليل.

### D — حالات التشغيل
- Skeleton يحافظ على أبعاد الجدول ولا يسبب قفزًا بصريًا.
- Empty state يفرّق بين «لا بيانات» و«لا نتائج للفلاتر» ويعرض الإجراء الصحيح.
- خطأ التحميل يعرض إعادة المحاولة دون فقد الفلاتر أو التخصيص.
- شريط الاختيار الجماعي ثابت وواضح، ويشرح هل التحديد للصفحة أم لكل النتائج.

## 4. بنية التنفيذ المقترحة

### المرحلة 0 — Gate شاشة الفواتير
1. مراجعة Evidence Pack الحالي لـ`OPA-UI-003`.
2. إغلاق الفجوات فقط إن وجدت، دون تعميم.
3. قرار بشري: Accept / Reject with findings.
4. لا تبدأ المرحلة التالية إلا بعد القبول.

### المرحلة 1 — Inventory & Contract Freeze
1. حصر كل شاشة جدول: مصدر البيانات، pagination، sorting، filters، selection، mobile mode، export.
2. تصنيفها إلى:
   - Server-paginated.
   - Client-side small dataset.
   - Virtualized/high-volume.
   - Financial/stock read-only surfaces تحت Smart Freeze.
3. تثبيت عقد موحّد للعرض وحالة الجدول، مع adapter لكل نمط قائم بدل rewrite.
4. تحديد الأعمدة المشتقة التي لا يجوز إرسال فلتر خادمي لها.
5. مخرج: Matrix للشاشات + frozen contract + قائمة استثناءات.

### المرحلة 2 — Canonical Interaction Kit
تطوير المكونات الحالية تدريجيًا، لا إنشاء نظام موازٍ:
1. `ColumnFilterHeader`: الأنواع، البحث، العدادات، keyboard/focus، loading/empty/error.
2. `ActiveFiltersBar`: شرائح مختصرة، overflow منظّم، saved views، نتيجة محدثة.
3. `TableViewOptions`: drag reorder، pinning المسموح، density، height، reset، keyboard fallback.
4. `useTableLayout`: versioning، user/screen scope، migration آمنة للتفضيلات القديمة.
5. عقد metadata لكل عمود يصف العرض والتفاعل فقط؛ mapping الاستعلام يبقى في Application/Query layer.
6. Story/test harness يغطي RTL، النص الطويل، الأرقام، الحالات، والبيانات الفارغة.

### المرحلة 3 — Query & Filter Reliability
1. إبقاء ترجمة الفلاتر في طبقة الاستعلام الحالية، لا في الصفحة ولا المكوّن.
2. اختبار مصفوفة `OR within column / AND across columns` لكل نوع.
3. remote option search للحقول كبيرة القيم بدل حد 500 الصامت؛ debounced، paginated، وآمن.
4. العدّ والصفوف والترقيم تستخدم نفس filter specification.
5. الفرز يكون خادميًا عندما تكون الصفحة خادمية؛ يمنع فرز الصفحة المحمّلة فقط على أنه فرز شامل.
6. التصدير والاختيار الجماعي يستهلكان نفس مواصفات البحث والفلاتر، مع حدود معلنة.
7. قياس عدد الطلبات والكمون قبل أي تحسين؛ resize/reorder/density = صفر طلبات بيانات.

### المرحلة 4 — Pilot Wave بعد الفواتير
الشاشات: **أوامر البيع → عروض الأسعار → أوامر الشراء → المنتجات → المدفوعات**.
لكل شاشة دفعة مستقلة:
1. Baseline حي.
2. تعريف column/filter metadata.
3. دمج المكونات القياسية مع query adapter الحالي.
4. معالجة المشتقات والعلاقات والاستثناءات.
5. تحقق كامل ثم Human Gate قبل الانتقال للشاشة التالية.

### المرحلة 5 — Rollout على بقية المشروع
- **Wave 2:** العملاء، الموردون، المصروفات، الخزينة، المهام والإشعارات.
- **Wave 3:** التقارير والسجلات عالية الكثافة والواجهات الافتراضية.
- **Wave 4:** المالية والمخزون — عرض/تحقق فقط ما لم يصدر تفويض مستقل لأي mutation أو semantic change.
- لا migration جماعية عمياء؛ يُستخدم النمط القياسي عند لمس الشاشة، مع دفعات صغيرة قابلة للرجوع.

### المرحلة 6 — Mobile & Responsive Data UX
- 360px: بطاقات أو قائمة ذات أولوية حقول، مع Filter Drawer كامل وملخص للفلاتر والعروض المحفوظة.
- 768px: جدول مضغوط بأعمدة أساسية، والباقي داخل التمرير/التخصيص.
- 1280px+: مساحة عمل كاملة مع resizing/reorder/pinning.
- نفس filter state والنتيجة على كل الأحجام؛ لا واجهة هاتف منفصلة بمنطق مختلف.

### المرحلة 7 — Accessibility & RTL Gate
- تنقل كامل بلوحة المفاتيح في الرأس، popovers، القوائم، الترتيب وتغيير العرض.
- focus واضح، أسماء ARIA، `aria-sort` للرؤوس، و`aria-live` للإعلان عن عدد النتائج وتغيّر الفرز.
- أهداف لمس 44px في الهاتف، وإغلاق overlays دون فقد الحالة.
- اختبار RTL/LTR للاتجاهات المنطقية ومقابض السحب والتثبيت.
- تباين AA وعدم الاعتماد على اللون وحده للحالة.

### المرحلة 8 — Performance & Observability
- Measure → Diagnose → Optimize → Measure Again.
- مؤشرات: first useful rows، زمن تطبيق الفلتر، عدد الطلبات، حجم payload، re-renders، سلاسة resize/scroll.
- إلغاء الطلب السابق عند البحث السريع، caching لقيم الفلاتر، وعدم تحميل القوائم إلا عند فتحها.
- virtualization فقط بعد تجاوز threshold مثبت بالقياس، لا كافتراض عام.
- budgets لكل نوع شاشة، مع مقارنة قبل/بعد.

## 5. معايير القبول لكل شاشة

### Layout
- عند 360/768/1280: `page scrollWidth === clientWidth`.
- التمرير المتوقع محصور داخل الجدول، الشريط الجانبي لا يغطي المحتوى، والترقيم كامل.
- الصفوف والعملات والحالات لا تلتف في الكثافات الثلاث.

### Filters & Query
- بحث العميل/المرجع/الحالة، multi-select، date range، number range.
- OR داخل العمود وAND بين الأعمدة مثبتان باختبار وحدة ودليل حي.
- count، pagination، rows، export وbulk selection متسقة.
- لا نتائج قديمة تظهر بعد تغيير سريع للفلاتر.

### Columns & Preferences
- resize ضمن min/max، auto-fit، hide/show، reorder، reset، density، height.
- لا طلبات بيانات أثناء تغييرات العرض.
- persistence بعد reload، وعزل صحيح بين المستخدمين والشاشات.

### Accessibility & Mobile
- تشغيل أساسي كامل بلوحة المفاتيح.
- focus/ARIA/contrast مقبول، و44px للأهداف الحرجة على الهاتف.
- الفلاتر النشطة قابلة للفهم والإزالة على الهاتف دون قص أو تجاوز.

### Regression
- لا تغيير business rules أو financial calculations أو permissions أو RLS أو migrations.
- لا direct DB access جديد من UI.
- typecheck، tests، fitness، والجولات الحية تمر دون regressions جديدة.

## 6. Evidence Pack لكل Batch

1. Scope وOut-of-scope.  
2. Frozen files والطبقات المحظورة.  
3. Baseline ولقطات/قياسات قبل التنفيذ.  
4. Static trace للصفحة → hook/query → repository الحالي.  
5. التغييرات المنفذة حسب Unit.  
6. أدلة 360/768/1280.  
7. Filter matrix والعدد/الترقيم.  
8. Network proof لعدم refetch في تغييرات العرض.  
9. Preference isolation/persistence.  
10. Keyboard/ARIA/RTL evidence.  
11. Visual evidence في RTL والوضعين الفاتح والداكن، ثم Performance before/after.  
12. Typecheck/tests/fitness.  
13. Out-of-scope findings وKnown limitations.  
14. Rollback note.  
15. Human Gate: `IMPLEMENTED ≠ VERIFIED ≠ ACCEPTED/CERTIFIED`.

## 7. ترتيب الأولوية المقترح

- **P0:** قص المحتوى، page overflow، count/pagination خاطئ، filter يغيّر معنى البيانات، أو تسرب تفضيلات مستخدم.
- **P1:** تناقض server filtering/selection/export، تعطل لوحة المفاتيح، أو ضعف استخدام يمنع رحلة فعلية.
- **P2:** saved views المركبة، pinning، remote facets، mobile filter drawer المحسن.
- **P3:** تحسينات مظهر أو كثافة لا تؤثر على التشغيل.

## 8. القرار المطلوب

1. قبول أو رفض `OPA-UI-003` كمرجع الفواتير.
2. عند القبول: تفويض **المرحلتين 1 و2 فقط** لإنتاج Inventory + Contract + Canonical Interaction Kit.
3. Pilot Wave وكل شاشة لاحقة تحتاج Gate منفصل؛ لا تفويض شامل مفتوح لكل المشروع.
