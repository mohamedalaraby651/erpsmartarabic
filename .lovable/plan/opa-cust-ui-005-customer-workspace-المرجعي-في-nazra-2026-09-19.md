# OPA-CUST-UI-005 — Customer Workspace المرجعي في Nazra

## الهدف والحدود
تحويل `/customers` من صفحة CRUD إلى مساحة تشغيل يومية للبحث والتصفية واتخاذ الإجراء والوصول إلى Customer 360، وجعلها **Reference Implementation** لنمط `Enterprise Data Workspace` دون تعميمه الآن.

- النطاق الحالي: العملاء فقط، عبر ثلاث دفعات مستقلة وبوابة قبول بين كل دفعة والتي تليها.
- إعادة استخدام النظام الحالي: `ColumnFilterHeader`، شريط الفلاتر النشطة، تفضيلات الجدول، Saved Views، مسار البحث، المستودعات، والتنقل الحالي.
- Smart Freeze: لا DB/RLS/migrations/permissions/roles، ولا تعديل لمنطق مالي/مخزون/انتقالات، ولا وصول مباشر للبيانات من UI.
- لا Metric جديد في الواجهة. أي قيمة مالية أو Health Indicator يجب أن تأتي من عقد تطبيق/استعلام موثوق موجود.
- لا تعميم على الموردين أو المنتجات أو الفواتير أو المبيعات أو المشتريات أو المخزون ضمن هذا التفويض.
- المخرجات تُوسم `IMPLEMENTED` و`VERIFIED` فقط. `HUMAN ACCEPTED` بوابة منفصلة، ولا self-certification.

## المرحلة 0 — Baseline وContract Discovery
1. تثبيت baseline قبل التعديل: زمن أول صفوف، عدد الطلبات عند البحث/الفلترة، تغير التخطيط، overflow، keyboard path، وأحجام 360/768/964/1280.
2. توثيق المسار: Page → hooks/query services → repositories → read models، والتأكد من عدم وجود DB access في UI.
3. جرد حقول العميل الفعلية وعقودها. `customer_code` و«مندوب المبيعات» لا يُضافان للواجهة إلا إذا كانا موجودين بالفعل ومتاحين عبر عقد القراءة؛ وإلا يسجلان `STOP/DEFERRED` بلا schema جديد.
4. تثبيت authority لكل Metric مرشح في Customer 360 قبل عرضه.

**بوابة G0:** baseline محفوظ + خريطة العقود + قائمة IMPLEMENT / DEFER / STOP، دون تعديل سلوكي.

## Batch A — Table Intelligence

### A1. هندسة الرأس المدمج
- دمج شريط «الكل / نشط / VIP / مدين / شركات / مزارع / أفراد / غير نشط» كصف وظيفي كامل داخل رأس الجدول على الشاشات الأكبر، فوق أسماء الأعمدة.
- إبقاؤه خارج الجدول في قائمة الهاتف، ومنع ظهوره مرتين في أي breakpoint.
- جعله مع أسماء الأعمدة رأسًا ثابتًا داخل scroll container الخاص بالجدول، مع بنية `<thead>/<tr>/<th>` سليمة، خلفية وحدود ومسافات متسقة.
- الحالة النشطة، الإلغاء، العدد، والتركيز بلوحة المفاتيح تبقى واضحة، ولا تتغير دلالة الفلاتر أو مصدر الإحصاءات.

### A2. Command Search موحّد
- حقل بحث واحد يدعم الاسم والهاتف والهاتف البديل والبريد والرقم الضريبي والحقول التعريفية الموجودة فعليًا، مع بحث جزئي ولصق مباشر.
- `Enter` يثبت التنفيذ، `Esc` يمسح/يغلق الاقتراحات حسب السياق، و`Ctrl/Cmd + K` ينقل التركيز للبحث دون الاستيلاء على الاختصار داخل الحقول أو الحوارات.
- إعادة استخدام مسار الاستعلام الحالي وdebounce الحالي؛ لا محرك بحث جديد ولا فلترة محلية لصفحة محملة فقط.
- إظهار زر مسح، حالة `isFetching` صغيرة، والاحتفاظ بالنتائج السابقة أثناء الطلب لمنع flicker.

### A3. فلاتر متكيفة مع نوع البيانات
- الاسم: بحث ثم Multi-select لعدة أسماء، مع إزالة فردية وبحث نصي حر بديل.
- الحالة والنوع وVIP: Multi-select.
- الرصيد وحد الائتمان والمشتريات: From/To.
- آخر نشاط وتاريخ الإنشاء: Date range.
- الهاتف والبريد والرقم الضريبي ومسؤول التواصل: Text operators الحالية.
- المحافظة/المدينة: searchable select عندما يكون المصدر الموثوق متاحًا؛ لا قائمة مشتقة من الصفحة المحملة فقط.
- مندوب المبيعات: Multi-select **فقط** إذا أثبتت المرحلة 0 وجود الحقل وعقد الخيارات؛ وإلا `DEFERRED`.
- خيارات أسماء العملاء تأتي من قراءة خفيفة ومحدودة ومخزنة مؤقتًا عبر repository/query hook الحالي، وتطبّق الفلاتر نفسها على النتائج والعدد والترقيم.

### A4. Active Filters وZero-result Recovery
- شريط واحد يعرض قيمًا مفهومة مثل «الحالة: نشط»، «الرصيد: أكبر من 10,000»، وأسماء العملاء المختارة، مع إزالة كل فلتر و«مسح الكل».
- عند كثرة الفلاتر: عرض الأهم ثم «+ N فلاتر أخرى» دون إخفاء إمكانية الإدارة.
- لا نتائج بسبب البحث/الفلاتر: اقتراح تقليل عبارة البحث أو إزالة فلتر مع زر مسح مباشر.
- لا بيانات أصلًا: دعوة إضافة/استيراد بحسب الصلاحية.
- خطأ التحميل: رسالة إعادة محاولة مستقلة؛ لا خلط بين الحالات الثلاث.

### A5. الاتساق والاستجابة
- count/list/filter/sort تستخدم الحالة نفسها، وإعادة القائمة للبداية عند تغير الاستعلام.
- Desktop/Tablet: جدول كامل بتمرير داخلي فقط. Mobile: بطاقات عميل مخصصة، لا جدول سطح مكتب مصغّر.
- الحفاظ على نتائج حالية أثناء refetch، skeleton لأول تحميل فقط، ومنع قفزات الواجهة.

### اختبارات وبوابة Batch A
- Unit: تحويل كل نوع فلتر، multi-name OR داخل العمود وAND بين الأعمدة، إزالة/مسح، serialization آمن.
- Integration: البحث والعدد والصفوف والترقيم متطابقة؛ لا ازدواج بين quick/legacy/column filters.
- Live: 360/768/964/1280، RTL، keyboard، focus، contrast، dropdown داخل viewport، لا page overflow أو نص مهم مقصوص.
- Performance: مقارنة baseline لزمن النتائج وعدد الطلبات وعدم إعادة الطلب عند resize/تخصيص العرض.

**Gate A:** `typecheck + focused/full tests + scoped lint + production build + live evidence` ثم Human Acceptance. لا يبدأ Batch B قبل قبوله.

## Batch B — Productivity

### B1. Saved Views كاملة
- توسيع آلية `user_saved_views` الموجودة، دون schema جديد، لحفظ الفلاتر العامة وفلاتر الأعمدة والبحث والترتيب، مع versioned payload وfallback للعروض القديمة.
- توفير Views جاهزة من الحالة الحالية مثل: الكل، المدينون، VIP، النشطون، آخر تعامل قديم؛ مع فصلها بصريًا عن «منظوري المحفوظ».
- حفظ/تطبيق/حذف/إعادة تسمية العرض، مع منع حفظ اسم فارغ ورسائل نجاح/فشل واضحة.

### B2. URL وعودة السياق
- تمثيل البحث والفلاتر والترتيب والعرض النشط في URL بصيغة محددة وقابلة للمشاركة، مع sanitize وحد أقصى للطول.
- URL له الأولوية عند الدخول المباشر؛ تفضيل المستخدم fallback عند غيابه.
- عند فتح Customer 360 ثم الرجوع: استعادة البحث والفلاتر والترتيب وموضع/صفحة القائمة، مع استمرار نمط navigation IDs الموجود.

### B3. تفضيلات الجدول
- الاستمرار في التخزين الحالي المرتبط بالمستخدم للأعمدة الظاهرة وترتيبها وعروضها والكثافة والارتفاع.
- إضافة حجم الصفحة/آخر ترتيب/آخر View إلى التفضيلات الموجودة إن كان عقدها يسمح، دون تخزين بيانات العملاء محليًا.
- ترحيل آمن للتفضيلات القديمة وReset يعيد defaults الصحيحة.

### B4. Keyboard-first
- `Ctrl/Cmd + K` للبحث، الأسهم للتنقل بين الصفوف عندما يكون الجدول مالك التركيز، `Enter` للفتح، `Space` للتحديد، و`Esc` يغلق أعلى طبقة أولًا.
- احترام Keyboard Ownership Guard: لا اختصارات عامة أثناء الكتابة أو عند فتح dialog/popover/menu.
- ترتيب Tab منطقي وfocus ظاهر وإعلان تغير عدد النتائج والتحديد عبر live region.

### B5. إجراءات الصف والهاتف
- سطح المكتب: إجراء أساسي واضح للفتح، ثم قائمة «المزيد» تجمع تعديل/فاتورة/دفعة/كشف حساب وباقي الإجراءات المتاحة بحسب الصلاحيات؛ لا شريط أزرار مزدحم.
- الهاتف: بطاقة تعرض الاسم والهاتف والحالة والرصيد وآخر نشاط المتاح، مع قائمة إجراءات واحدة بحد لمس 44px.
- لا يظهر إجراء دون صلاحية أو دون route/handler عامل.

### B6. Prefetch محدود
- البناء فوق prefetch الحالي بتأخير hover/focus، dedupe، cache، وإلغاء المؤقت عند المغادرة؛ لا prefetch على اللمس أو المرور السريع.
- قياس عدد الطلبات ومنع fan-out. يبقى prefetch عبر query/repository فقط.

### اختبارات وبوابة Batch B
- رحلات حفظ View وتطبيقه والعودة من التفاصيل واستعادة السياق.
- keyboard-only وscreen reader labels وصلاحيات الإجراءات.
- قياس عدد الخطوات والزمن لرحلات: إيجاد عميل، تصفية مدينين، فتح/عودة، إصدار فاتورة، تسجيل دفعة.

**Gate B:** أدلة workflow/performance/accessibility + Human Acceptance قبل Batch C.

## Batch C — Customer 360 الموثوق

### C1. Health Snapshot في القائمة
- عرض الرصيد وآخر نشاط وحالة الحساب الموجودة في read model فقط، بهرم بصري مختصر على Desktop/Mobile.
- لا اشتقاق «صحة العميل» أو DSO أو CLV أو overdue داخل UI.

### C2. ملخص Customer 360
- عرض إجمالي المبيعات والمدفوعات والرصيد وآخر فاتورة وآخر دفعة فقط من Query Service/RPC/authoritative read model قائم ومثبت.
- لكل قيمة: تعريف، مصدر، tenant boundary، precision، empty/error state، وتاريخ التحديث إن كان cached.
- أي Metric بلا authority مثبت ينتقل إلى `STOP/DEFERRED` ولا يُقرب حسابه في الواجهة.

### C3. Customer Operations
```text
البحث + الفلاتر + Views
           ↓
     Customer Table
           ↓
تفاصيل | كشف حساب | فاتورة | دفعة
           ↓
      Customer 360
```
- إبقاء الانتقال بين القائمة والتفاصيل والإجراءات محافظًا على سياق المستخدم.
- لا تعديل في سلطة إنشاء المستندات أو الدفعات أو الحسابات؛ المرحلة تربط الإجراءات القائمة فقط.

### اختبارات وبوابة Batch C
- مقارنة كل Metric بمصدره الموثوق وعينات بيانات فعلية، مع حالات null/error/stale.
- تحقق صلاحيات العرض، RTL، الهاتف، ودقة منزلتين للقيم المالية المعروضة.

**Gate C:** VERIFIED تقنيًا ثم مراجعة بشرية مستقلة؛ لا CERTIFIED ذاتيًا.

## بوابة الأداء وقرار Virtualization
- القياس أولًا: حجم البيانات، DOM rows، زمن أول عرض، زمن filter settle، scroll FPS، memory، وعدد الطلبات.
- server-side pagination يبقى المصدر الموثوق. لا virtualization إذا حقق الجدول الميزانية المتفق عليها.
- إذا أثبت القياس الحاجة، يصدر قرار معماري مستقل يحدد توافق virtualization مع sticky header، selection، keyboard، row height، وRTL قبل التنفيذ.

## مخرج Reference Implementation
- توثيق عقد `Enterprise Data Workspace`: تركيب الرأس، أنواع الفلاتر، query consistency، states، keyboard، mobile، saved views، التفضيلات، القياس، وحدود الصلاحيات.
- إضافة Fitness/Regression checks لما يمكن قياسه آليًا دون فرضه على بقية الصفحات.
- التعميم اللاحق يبدأ بجرد واختيار أعمدة مناسبة لكل نطاق، لا بنسخ آلي ولا ضمن OPA-CUST-UI-005.

## حالات التوقف الصريحة
- غياب `customer_code` أو sales-representative contract.
- حاجة أي Metric إلى SQL/RPC/schema/RLS أو منطق مالي جديد.
- تعارض Saved Views الموسعة مع payloads القديمة دون migration آمن داخل JSON.
- فلاتر تُطبّق على الصفوف المحملة فقط بينما العدد يوحي بأنها server-wide.
- رغبة في select-all عبر كل النتائج أو تغيير offset pagination بعد mutations؛ كلاهما تفويض معماري مستقل.
