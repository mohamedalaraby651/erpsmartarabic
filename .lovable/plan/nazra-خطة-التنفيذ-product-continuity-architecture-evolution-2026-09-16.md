# NAZRA — خطة التنفيذ: Product Continuity + Architecture Evolution

الفلسفة المعتمدة: **Build the product while hardening the platform.** ما يمنع المستخدم من العمل أو يهدد سلامة البيانات/الأمان يُعالج أولًا؛ الدين المعماري غير المؤثر تشغيليًا يُعالج تدريجيًا أثناء التطوير. الحوكمة تبقى قائمة: لا Certification ذاتي، Smart Freeze نشط على (الدفاتر، الدفعات، حركة المخزون، المزامنة، سلطة الـtenant، الصلاحيات، RLS، الترحيلات) إلا بنطاق مُصرَّح.

## نموذج الأولوية

| المستوى | التعريف | المعالجة |
|---|---|---|
| P0 | النظام لا يعمل / خطر أمني أو فقدان بيانات | فورًا، يوقف ما عداه |
| P1 | Workflow أساسي لا يكتمل | في الدفعة الحالية |
| P2 | UX / أداء سيئ لكن العمل ممكن | Sprint قريب |
| P3 | دين معماري بلا أثر تشغيلي | تدريجي أثناء التطوير |

## المسار (أ) — Product Continuity

### المرحلة 1 — إغلاق POSTF1 (منفّذ، يحتاج تحقق)
Unit A (الإشعارات عبر RPC مشتق الـtenant) وUnit B (`paid_amount`) منفّذان بالفعل. المطلوب: تحقق مستقل بلا تعديل مصدر يثبت الحفظ، القراءة، عزل الـtenant، منع الانتحال داخل نفس الـtenant، رفض `anon`، رفض الإدراج المباشر، وظهور الفواتير الأخيرة بلا أخطاء. المخرج: سجل تحقق + دليل JSON + حكم PASS/FAIL/BLOCKED.

### المرحلة 2 — Operational Product Audit (على النسخة الحالية نفسها)
فحص تشغيلي مباشر للكود الحيّ، لا اعتماد على أرقام F0/F1 القديمة. يغطي:
- كل الصفحات والمسارات الفعلية في `App.tsx`.
- كل زر/إجراء استهلاكي: المعالج الحقيقي، الطبقة، المستودع/RPC، السلطة، الجداول، انتقال الحالة، رسائل النجاح/الخطأ، إبطال الكاش، نظير الموبايل.
- النماذج، البحث، الفلاتر، الحوارات، الإشعارات، الطباعة، التقارير، الصلاحيات، حفظ البيانات.
المخرج: مصفوفة تشغيل حقيقية (CSV/JSON + وثيقة) وBacklog مصنّف P0/P1/P2/P3.

### المرحلة 3 — إصلاح P0 من نتائج التدقيق
أزرار معطّلة، شاشات لا تحفظ، بيانات لا تظهر، أعطال صلاحيات، أعطال طباعة حرجة. كل إصلاح يمسّ منطقة Smart Freeze يُفتح له نطاق مستقل بأدلة.

### المرحلة 4 — اكتمال الرحلات الأساسية (End-to-End بلا طريق مسدود)
- المبيعات: عميل ← عرض سعر ← اعتماد ← أمر بيع ← فاتورة ← دفعة ← طباعة ← إشعار ← تقرير.
- المشتريات: مورد ← أمر شراء ← استلام ← فاتورة شراء ← دفعة ← طباعة ← محاسبة.
- المخزون: منتج ← رصيد افتتاحي ← شراء/استلام ← حركة ← بيع ← خصم ← تقرير (تطابق الرقم المعروض مع ما حدث فعلًا).
- المالية: فاتورة ← ترحيل ← ذمم ← دفعة ← دفتر ← رصيد ← تقارير (تحت نطاق محكوم).
- الموارد البشرية: موظف ← حضور ← إجازة ← تقارير.

### المرحلة 5 — UX / الأزرار والتغذية الراجعة
حالات: عادي / معطّل / تحميل / نجاح / خطأ / تأكيد للعمليات الخطرة، منع الإرسال المزدوج، حالات فارغة، رسائل عربية مفهومة، تقليل عدد الشاشات لإنهاء المهمة الواحدة.

### المرحلة 6 — الطباعة كـWorkstream مستقل
عرض سعر، فاتورة، أمر شراء، أمر بيع، إيصال دفع، تقارير: RTL، بيانات الشركة، الشعار، التواريخ، العملة، الإجماليات، الضريبة، فواصل الصفحات، A4، إيصال حراري عند اللزوم، طباعة المتصفح وPDF — مع تطابق المستند المطبوع مع حالة العمل المعروضة.

### المرحلة 7 — النسخ الاحتياطي والاسترجاع
فصل صريح بين تصدير بيانات التطبيق، والنسخ من المزوّد، والتعافي من الكوارث. توثيق وإثبات: الاكتمال، صحة الاسترجاع، سلامة الـtenant، الاحتفاظ، الجدولة، RPO/RTO، وإجراء تعافٍ قابل للتنفيذ.

### المرحلة 8 — الأداء: قياس ثم إصلاح
قياس التحميل الأولي، لوحة التحكم، التنقل، الاستعلامات، الجداول، النماذج، البحث، الطباعة، الموبايل؛ ثم تحسين الاختناقات المقاسة فقط.

### المرحلة 9 — الموبايل/PWA للرحلات الحرجة
الدخول، لوحة التحكم، العملاء، المبيعات، الفواتير، الدفعات، الإشعارات — قبل أي توسّع لبقية المسارات.

### المرحلة 10 — إتاحة الوصول وRTL ثم Design System
البدء بالنماذج والجداول والحوارات والتنقل والأزرار والتركيز ولوحة المفاتيح، ثم توسعة تدريجية. نظام التصميم: ترسيخ العناصر القياسية، إلزام التطوير الجديد بها، وترحيل الشاشات القديمة تدريجيًا.

## المسار (ب) — Architecture Evolution (بالتوازي، حسب الأثر)

- تصنيف المخالفات المتبقية إلى: خطِرة تشغيليًا (الآن) / تعيق ميزة نشطة (أثناء الميزة) / دين معماري (تدريجي) / انتقالية مشروعة (لا إصلاح).
- F2 يتحول إلى Architecture Backlog محكوم بالأثر: أي استدعاء Supabase مباشر داخل ميزة نُعدّلها يُحوَّل إلى facade أثناء العمل عليها؛ ولا نوقف المنتج لتحويل ما لا نلمسه.
- الحدود BND-01..04 و06..08 تُعالج بأولوية المخاطر لا بالتسلسل الأعمى؛ BND-05 يبقى معتمدًا.
- المخاطر المفتوحة RISK-007 / RISK-008 / PRE-EXT-001 تبقى مفتوحة، وPRE-TS-001 يُسجَّل كـDELTA محتوى عند كل تكرار.

## قاعدة منع الدين الجديد

أي ميزة أو إصلاح جديد يسلك: صفحة ← تطبيق ← نطاق/خدمة ← مستودع ← قاعدة بيانات، ويستخدم العناصر القياسية وTokens وقواعد RTL واصطلاحات الحالة. لا استدعاء قاعدة بيانات مباشر من الواجهة في أي كود جديد.

## تفاصيل تقنية

- أدوات: `scripts/audits/*`، `scripts/fitness/run-all.mjs`، `scripts/audits/typecheck-app.mjs`، Vitest، Playwright (`e2e/`).
- سكربت جديد لمصفوفة التشغيل يستخرج المسارات من `App.tsx` ويتتبع الإجراءات من الواجهة إلى المستودع/RPC، ويكتب المخرجات في `scripts/audits/output/`.
- الأدلة الحيّة عبر استعلامات قاعدة البيانات واستدعاءات حقيقية بهوية مستخدم، لا `SET ROLE`.
- سجلات الحوكمة تحت `docs/governance/`، وتحديث `roadmap.md` بمسار المنتج الجديد ومهامه.

## ما سأنفّذه فور الموافقة

1. تحديث `roadmap.md` باعتماد المسارين والأولويات الجديدة.
2. المرحلة 1: التحقق المستقل من POSTF1 (بلا تعديل مصدر).
3. المرحلة 2: تنفيذ Operational Product Audit وإخراج مصفوفة التشغيل وBacklog مصنّف P0–P3.

ثم أعرض نتائج P0 لتقرّر ترتيب الإصلاح قبل بدء المرحلة 3.
