# NAZRA — Product Requirements Baseline (PRB)

**معرّف الوثيقة:** `PRB-NAZRA-001`  
**الإصدار:** `1.0` — Baseline بعد استكمال الاستبيان  
**النطاق:** Product Vision + Business Requirements + Functional Requirements + Architecture Direction + Governance + Delivery Roadmap  
**السوق الأول:** جمهورية مصر العربية  
**الحالة:** `CANDIDATE FOR HUMAN ACCEPTANCE`  
**نوع الوثيقة:** مرجع متطلبات مرشح للاعتماد البشري، وليس عقد تنفيذ.

---

## 0. تعليمات القراءة والاستخدام بواسطة الذكاء الاصطناعي داخل Lovable

### 0.1 الغرض

هذه الوثيقة هي المرجع الأعلى لمتطلبات المنتج في مشروع Nazra بعد تجميع إجابات الاستبيان. تُستخدم لفهم **ما الذي يجب أن يقدمه المنتج ولماذا**، ولإنشاء خرائط التتبع والمتطلبات التفصيلية وعقود التنفيذ وخطط الاختبار بعد الاعتماد البشري.

### 0.2 قواعد إلزامية على أي وكيل ذكاء اصطناعي يقرأ الوثيقة

1. تعامل مع هذه الوثيقة باعتبارها **Candidate Baseline** إلى أن يصدر اعتماد بشري صريح.
2. لا تعتبر أي متطلب مذكور هنا دليلًا على أن الوظيفة موجودة أو نُفذت أو اختُبرت أو أصبحت جاهزة للإنتاج.
3. لا تنفذ تغييرات في الكود أو قاعدة البيانات أو RLS أو الصلاحيات أو البيانات أو البنية التحتية لمجرد قراءة هذه الوثيقة.
4. لا تنشئ Migration أو Edge Function أو جدولًا أو API أو شاشة أو Repository أو خدمة قبل وجود عقد تنفيذ معتمد يحدد النطاق ومعايير القبول والأثر وخطة التحقق.
5. لا تملأ القرارات المفتوحة بافتراضات. احتفظ بها في سجل القرارات المفتوحة، واطلب قرارًا بشريًا قبل بناء سلوك يعتمد عليها.
6. افصل دائمًا بين:
   - **متطلب مؤكد:** صرّح به المستخدم ضمن إجابات المتطلبات.
   - **استنتاج:** توصية أو تصميم مستنتج، لا يصبح قرارًا معتمدًا تلقائيًا.
   - **قرار مفتوح:** لم يُحسم بعد.
   - **حالة التنفيذ:** PLANNED / IMPLEMENTED / VERIFIED / HUMAN ACCEPTED / APPROVED.
7. لا ترفع حالة أي بند من PLANNED إلى IMPLEMENTED أو VERIFIED أو HUMAN ACCEPTED أو APPROVED دون دليل مناسب لكل مرحلة.
8. عند تعارض هذه الوثيقة مع حالة المستودع الفعلية، سجّل التعارض وأظهر الدليل؛ لا تغيّر الوثيقة أو الكود بصمت.
9. استخدم أسلوب Strangler Fig والتطوير التدريجي. لا تقترح Rewrite شاملًا أو Microservices دون مبرر موثق واعتماد.
10. التزم بمبدأ عدم وجود DB Client داخل UI، وعدم وضع منطق الأعمال الجوهري داخل Components، مع التحقق من الواقع الحالي قبل وصفه بأنه مطبق.
11. جميع حدود الأمان والمال والمخزون وعزل الشركات تتطلب تحققًا خادميًا واختبارات قابلة للتكرار.
12. لا تستخدم أرقامًا تاريخية عن Routes أو الجداول أو Repositories أو الاختبارات على أنها أرقام حالية. يجب إعادة قياسها من المستودع عند تنفيذ Phase 0.
13. لا تُنشئ مواصفات ضريبية مصرية أو متطلبات تكامل حكومي من الذاكرة أو التخمين؛ يجب التحقق من المصادر الرسمية عند تصميم التنفيذ.
14. اللغة الافتراضية للمنتج عربية، والاتجاه RTL أصلي. يمكن استخدام أسماء المجالات والمصطلحات التقنية الإنجليزية كما هي عند الحاجة.
15. كل تغيير تنفيذي لاحق يجب أن يرتبط بمتطلب أو قرار معتمد، وبـ Contract ID، واختبارات، وEvidence Pack، وStop Conditions، وخطة Rollback/Recovery.

### 0.3 سلم موثوقية المعلومات

| الوسم | المعنى | طريقة التعامل |
|---|---|---|
| `[متطلب مؤكد]` | مطلب صرّح به المستخدم | يُحفظ كما هو، ويحتاج تفصيلًا تنفيذيًا عند اللزوم |
| `[استنتاج]` | توصية أو نموذج مقترح | لا يُعامل كقرار حتى اعتماده |
| `[قرار مفتوح]` | مسألة لم تُحسم | لا يُفترض لها سلوك تنفيذي |
| `[غير متحقق]` | لم تتم مراجعة المستودع أو الدليل اللازم | لا تصف الحالة بأنها موجودة أو ناجحة |
| `[دليل مطلوب]` | يتطلب إثباتًا | حدّد نوع الدليل واختبار القبول |

### 0.4 الفرق بين أنواع الوثائق

- **PRB:** يحدد رؤية المنتج ومتطلباته واتجاهه العام.
- **Detailed Requirement:** يحول المتطلب إلى سلوك محدد وقابل للاختبار.
- **Architecture Decision Record (ADR):** يوثق قرارًا معماريًا مع البدائل والمبررات.
- **Implementation Contract:** يحدد تغييرًا تنفيذيًا محدودًا ومعتمدًا.
- **Test Strategy / Test Case:** يحدد طريقة التحقق والنتيجة المتوقعة.
- **Evidence Pack:** يجمع أدلة التنفيذ والاختبار.
- **Acceptance Record:** يسجل قبول الإنسان أو اعتماده صراحة.

# 1. الرؤية الاستراتيجية للمنتج

## 1.1 الرؤية

إنشاء نظام ERP عربي متكامل، قابل للتوسع التجاري، يخدم الشركات الصغيرة والمتوسطة أولًا، مع قابلية التدرج إلى احتياجات الشركات الكبيرة وبيئات Enterprise.

يدير Nazra بصورة موحدة:
- المبيعات والعملاء.
- المشتريات والموردين.
- المخزون والمخازن والفروع.
- المحاسبة والمالية.
- الموظفين والمهام.
- التقارير والتحليلات.
- الموافقات والحوكمة.
- المستندات والتكاملات.
- الذكاء الاصطناعي والأتمتة.

## 1.2 السوق والعملاء

| العنصر | المتطلب |
|---|---|
| السوق الأول | مصر |
| القطاع ذو الأولوية | التجارة العامة والتوزيع |
| القطاعات المستقبلية | جميع أنواع الأنشطة والشركات |
| العميل الأساسي | الشركات الصغيرة، خصوصًا 6–20 موظفًا |
| مستوى المنتج | Enterprise تدريجيًا مع سهولة الاستخدام |
| الاستراتيجية التجارية | منصة قابلة للتوسع التجاري من البداية |

## 1.3 فلسفة المنتج

- نواة ERP مشتركة.
- تخصيص حسب الشركة والنشاط.
- وحدات قابلة للتفعيل والتخصيص.
- تجربة عربية أصلية RTL.
- سهولة بدء الاستخدام.
- التوسع دون الحاجة إلى إعادة بناء المنتج.

`[استنتاج]` يفضل أن يكون التخصيص قائمًا على إعدادات وامتدادات محكومة، لا على نسخ كود منفصل لكل عميل.

`[قرار مفتوح: OD-15]` هل تشمل المرحلة الأولى أوامر الإنتاج وBOM ومراحل التصنيع، أم يقتصر الدعم على تعريف المنتجات المصنعة وتكلفتها ومخزونها؟

# 3. متطلبات المبيعات والمشتريات

## 3.1 المبيعات

### قنوات البيع
- البيع المباشر من مقر الشركة.
- البيع من الفروع.
- البيع بالتجزئة.
- الطلبات الهاتفية.
- طلبات WhatsApp.

`[متطلب مؤكد]` مسارات بيع قابلة للتكوين حسب الشركة.

`[استنتاج]` المسار المرجعي المقترح:

`Customer → Quotation → Sales Order → Delivery → Invoice → Payment`

يجب أن تدعم دورة البيع تتبع مصدر كل مستند وعلاقته بالمستند السابق.

### الوظائف
- إدارة العملاء.
- عروض الأسعار.
- أوامر البيع.
- الفواتير.
- التسليم.
- الدفعات الجزئية والمتعددة.
- البيع الآجل.
- حدود الائتمان.
- متابعة التحصيل.
- المرتجعات بمراجعة وموافقة.

## 3.2 المشتريات

`[متطلب مؤكد]` مسارات شراء مختلفة حسب المورد والعملية.

`[استنتاج]` المسار المرجعي:

`Supplier → Purchase Order → Goods Receipt → Purchase Invoice → Supplier Payment`

يجب فصل طلب الشراء عن الاستلام وعن فاتورة المورد وعن السداد.

## 3.3 المرتجعات

`[متطلب مؤكد]` لا تعتمد المرتجعات تلقائيًا؛ بل تمر بمراجعة وموافقة.

`[استنتاج]` يجب فصل الحالات التالية:
- طلب مرتجع.
- مراجعة الطلب.
- الموافقة أو الرفض.
- الاستلام الفعلي للمرتجع.
- تقييم حالة المنتج.
- الأثر المخزني.
- الأثر المالي والمحاسبي.

## 4.2 الوظائف المطلوبة

- أرصدة المخزون.
- حركات الاستلام والصرف.
- التحويلات.
- الجرد.
- التسويات المخزنية.
- تقييم المخزون.
- تكلفة البضاعة المباعة.
- حدود إعادة الطلب.
- التنبيه عند نقص المخزون.

## 4.3 قواعد سلامة المخزون

`[استنتاج]` يجب أن تكون حركات المخزون ذات مصدر واضح وأثر قابل للتتبع، مع منع ازدواج تنفيذ الحركة عند إعادة إرسال الطلب.

### قرارات مفتوحة
- `[OD-04]` طريقة تقييم المخزون: متوسط مرجح أم FIFO أم غير ذلك؟
- `[OD-05]` هل يسمح بالمخزون السالب؟ وهل يكون ذلك حسب إعداد الشركة؟
- هل يتطلب الجرد اعتمادًا قبل ترحيل التسوية؟
- هل يشمل التصنيع إدارة BOM ومراحل الإنتاج؟ انظر OD-15.

# 5. المحاسبة والمالية والضرائب

## 5.1 المستوى المحاسبي

`[متطلب مؤكد]` البدء بمحاسبة متكاملة، ثم التوسع تدريجيًا إلى المستوى المتقدم.

النطاق المستهدف:
- دليل الحسابات.
- القيد المزدوج.
- دفتر الأستاذ.
- قيود اليومية.
- الترحيل التلقائي للعمليات المعتادة.
- القيود اليدوية للعمليات الاستثنائية.
- مراكز التكلفة.
- الميزانيات.
- التحليلات المالية.
- الرقابة والتدقيق المالي تدريجيًا.

## 5.2 قواعد إنشاء القيود

`[متطلب مؤكد]`
- العمليات المعتادة: إنشاء القيود تلقائيًا.
- العمليات الاستثنائية: ينشئها المحاسب يدويًا.

`[استنتاج]` يجب أن يكون لكل قيد مصدر تشغيلي واضح، مع إمكانية تتبع القيد إلى الفاتورة أو الدفع أو الحركة الأصلية.

## 5.3 العملة

- العملة الأساسية والوحيدة المطلوبة: الجنيه المصري.
- لا يوجد حاليًا متطلب لتعدد العملات أو فروق أسعار الصرف.

## 5.4 الائتمان والتحصيل

المتطلبات:
- حد ائتماني لكل عميل.
- متابعة المديونية.
- أعمار الديون.
- التحصيلات.
- الموافقات.
- التنبيهات.

`[قرار مفتوح: OD-03]` هل يؤدي تجاوز الحد الائتماني إلى تنبيه فقط، أم منع البيع، أم منع التسليم، أم السماح بالتجاوز بعد موافقة مسؤول مخول؟

## 5.5 الفترات المالية

المتطلب الحالي: عرض تقارير حسب الفترة دون إقفال رسمي.

لا يُعد الإقفال الشهري أو السنوي الرسمي متطلبًا محسومًا في هذه المرحلة.

`[استنتاج]` يجب الاحتفاظ بتاريخ العملية وتاريخ الترحيل، حتى يمكن تحديد أثر تعديل البيانات القديمة على التقارير.

## 5.6 الضرائب والفوترة الإلكترونية

الاستراتيجية:
- البدء بالأساسيات.
- التوسع تدريجيًا.
- دعم المتطلبات الضريبية المصرية.
- إضافة التكاملات الضريبية وفق المتطلبات الرسمية التي يتم التحقق منها عند التنفيذ.

## 5.7 التقارير المالية

التقارير المطلوبة:
1. ميزان المراجعة.
2. قائمة الدخل.
3. الميزانية العمومية.
4. التدفقات النقدية.
5. كشوف حسابات العملاء والموردين.
6. أعمار الديون والتحصيلات المتأخرة.
7. مراكز التكلفة والربحية.
8. مقارنة الفترات.
9. تقارير الميزانيات.

**معيار أساسي:** يجب أن تتطابق التقارير مع القيود والحركات الفعلية، لا أن تعتمد على أرقام مستقلة محسوبة في الواجهة.

# 12. التوجه المعماري المقترح

**تنبيه:** هذا القسم يمثل اتجاهًا هندسيًا مستندًا إلى وثائق handoff، وليس تصريحًا بأن جميع الحدود متحققة حاليًا في المستودع.

## 12.1 Architecture Style

Modular Monolith.

لا يوجد مبرر حالي لإعادة كتابة النظام أو التحول إلى Microservices.

## 12.2 طبقات النظام

```text
Presentation / UI
        ↓
Application / Use Cases
        ↓
Domain
        ↓
Repositories
        ↓
Supabase / PostgreSQL
```

## 12.3 التقنية المرجعية

وفق وثيقة handoff:
- React 18.
- TypeScript 5.
- Vite 5.
- Tailwind CSS 3.
- shadcn/ui.
- Radix UI.
- TanStack Query.
- Supabase.
- PostgreSQL.
- RLS.
- Edge Functions.
- jsPDF.
- XLSX.
- Recharts.

هذه قائمة التقنية الموثقة تاريخيًا، وليست إعادة تحقق من كل إصدار مستخدم في المستودع الحالي.

## 12.4 قواعد معمارية

- لا DB Client داخل UI.
- لا Business Logic جوهري داخل Components.
- المستودعات هي حدود الوصول إلى البيانات.
- Query Services للقراءات المركبة.
- منطق المال والمخزون في طبقات موثوقة.
- Tenant Isolation على مستوى الخادم وقاعدة البيانات.
- Strangler Fig بدل Rewrite.
- Event Sourcing ليس نمطًا عامًا للنظام؛ استثناء الفواتير يظل محدودًا بتصميمه الحالي.

# 16. منهج التنفيذ والحوكمة

## 16.1 متطلبات كل Batch تنفيذي

كل Batch تنفيذي يجب أن يحتوي على:
1. Contract ID.
2. Scope.
3. Out of Scope.
4. Dependencies.
5. Affected Layers.
6. Database Impact.
7. Security Impact.
8. Acceptance Criteria.
9. Verification Plan.
10. Evidence Pack.
11. Stop Conditions.
12. Rollback / Recovery.
13. Human Acceptance.

## 16.2 قواعد سلامة البيانات

- لا حذف نهائي للمستندات المالية.
- RLS وعزل Tenant لكل جدول جديد.
- تقريب مالي موحد.
- اختبار لكل قاعدة مالية.
- نسخة احتياطية قبل Migration حساس.
- تنفيذ تدريجي مع اختبار وعرض النتائج.
- لا تعديل لقيود تاريخية لمجرد تصحيح العرض.

## 16.3 مستويات إثبات الإنجاز

```text
PLANNED
   ↓
IMPLEMENTED
   ↓
VERIFIED
   ↓
HUMAN ACCEPTED
   ↓
APPROVED
```

لا يجوز دمج هذه الحالات أو اعتبار التنفيذ دليلًا على التحقق.

## 16.4 أسلوب التطوير

- Modular Monolith.
- Strangler Fig.
- أصغر تغيير متماسك.
- عدم تنفيذ Rewrite شامل.
- عدم التوسع إلى Microservices دون مبرر موثق.
- عدم تغيير حدود الأمان أو المالية أو المخزون ضمنيًا.
- تتبع كل متطلب إلى تنفيذ واختبار ودليل.

# 18. قرار الاعتماد المطلوب

هذه الوثيقة تمثل Baseline متكاملًا للمتطلبات المستخلصة من الدفعات التسع، لكنها لا تعني:
- أن جميع الوظائف موجودة في النظام.
- أن جميع المتطلبات معتمدة هندسيًا.
- أن كل وحدة جاهزة للإنتاج.
- أن خارطة الطريق بدأت بالتنفيذ.
- أن الاختبارات أو الشهادات قد اجتازت بالفعل.

**الحالة المقترحة:** `PRB-NAZRA-001 — CANDIDATE FOR HUMAN ACCEPTANCE`

بعد الاعتماد البشري الصريح، تصبح الوثيقة مرجعًا لاشتقاق:
- Product Architecture.
- Domain Boundaries.
- Detailed Requirements.
- Implementation Contracts.
- Test Strategy.
- Delivery Batches.
- Product Readiness Gates.

**لا يُعد رفع الملف إلى Lovable أو قراءته بواسطة الذكاء الاصطناعي اعتمادًا بشريًا، ولا يمنح إذنًا بالتنفيذ.**

# 20. تعليمات تشغيلية مختصرة لوكيل Lovable

عند استلام طلب عمل مرتبط بهذه الوثيقة:

1. حدد `Requirement ID` أو القسم المرتبط بالطلب.
2. افحص الحالة الفعلية في المستودع قبل اقتراح التنفيذ.
3. أنشئ مصفوفة Traceability: Requirement → Existing Code → Gap → Contract → Tests → Evidence.
4. ميّز ما هو مثبت في المستودع عما هو موثق في PRB فقط.
5. افحص Dependencies وSecurity/Database/Financial/Inventory Impact.
6. اعرض القرارات المفتوحة ذات الصلة ولا تحسمها نيابة عن المستخدم.
7. اقترح أصغر Batch متماسك، مع Scope وOut of Scope واضحين.
8. لا تبدأ التنفيذ قبل اعتماد العقد والقرارات اللازمة.
9. بعد التنفيذ، لا تدّعِ VERIFIED دون تشغيل الاختبارات وفحص الأدلة.
10. اطلب Human Acceptance قبل إغلاق بوابة القبول.

**المبدأ الحاكم:** PRB يحدد اتجاه المنتج ومتطلباته؛ المستودع يثبت الحالة الحالية؛ العقد المعتمد يجيز التغيير؛ الاختبارات والأدلة تثبت النتيجة؛ والإنسان وحده يمنح القبول والاعتماد.
