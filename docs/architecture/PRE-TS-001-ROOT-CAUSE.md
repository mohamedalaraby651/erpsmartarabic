# PRE-TS-001 — Root-Cause Investigation (Platform Regeneration Drift)

- **Status:** ROOT CAUSE RESOLVED — see §8 (Control 1 decision). Ownership control now in place.
- **Phase:** Phase 0 (investigation) → Post-Exit Control Resolution, Control 1 (decision)
- **Recurrences:** 7 (recurrence #7 observed during Control 1 and diagnosed correctly for the first time)
- **Boundary:** cross-cutting — artifact ownership at the platform boundary (feeds BND-01)

> Phase 0 explicitly does **not** re-apply the annotation, does not reopen C2, and does not
> change generator behaviour. The question is ownership, not syntax.

## 1. Symptom

`npx tsgo -p tsconfig.app.json --noEmit` fails with `TS7011` (function expression lacking a
return-type annotation, implicitly `any`) in
`src/integrations/supabase/previewAuthStorage.ts`. The failure reappears after platform
regeneration of that file, regardless of prior fixes.

## 2. Investigation chain

```text
Why is the file regenerated?  → What is the canonical source?  → Which generator?
      → What is the regeneration trigger?  → Who owns the artifact?  → How do we prevent drift?
```

| # | Question | Finding |
|---|---|---|
| 1 | Why is the file regenerated? | It is a **platform-managed integration artifact**, re-emitted by the hosting platform whenever the preview-auth brokering template changes or the project's integration scaffold is refreshed. Regeneration is not triggered by our commits. |
| 2 | What is the canonical source? | **Not in this repository.** The canonical source is the platform's preview-auth storage template. The repo copy is an *output*, marked `// This file is automatically generated. Do not edit it directly.` |
| 3 | Which generator? | The Lovable Cloud / Supabase integration scaffolder that also owns `src/integrations/supabase/client.ts` and `types.ts`. |
| 4 | What is the regeneration trigger? | Platform-side template revision or integration refresh — outside our control and outside our change-classification gate. |
| 5 | Who owns the artifact? | **The platform, not the project.** The project owns *consumption*, not content. |
| 6 | How do we prevent drift? | Not by editing the artifact. Only by changing how the project's typecheck contract treats platform-owned generated files. |

## 3. Root cause (stated plainly)

> A **platform-owned generated artifact is being held to a project-owned strictness
> contract.** Our `tsconfig.app.json` applies `noImplicitAny`-class strictness to a file we
> neither author nor control. Every "fix" edits an output, so the next regeneration
> overwrites it. The recurrence is structural and will continue indefinitely.

This is a **boundary-ownership defect**, not a TypeScript defect. Recurrence count is the
evidence: five identical repairs, five identical regressions, zero durable change.

## 4. Why opportunistic repair is now formally insufficient

Each repair costs a preflight micro-change, perturbs evidence lineage, and creates false
confidence that the issue is managed. Repair #6 would produce exactly the same outcome as
repairs #1–#5. Per ADR-0031 R-BND-7, an unowned artifact cannot be declared enforced.

## 5. Candidate resolutions (specified, none authorized here)

| Option | Description | Cost | Risk |
|---|---|---|---|
| A | Exclude platform-generated `src/integrations/**` from the strict app typecheck project, and typecheck project code only | low | loses type feedback on generated files (which we cannot fix anyway) |
| B | Add a dedicated looser tsconfig project for generated integration artifacts | medium | two typecheck projects to keep aligned |
| C | Wrap consumption behind a project-owned adapter and stop referencing the artifact directly from app code | medium-high | real boundary improvement; largest change surface |
| D | Request the platform emit annotated output | none locally | outside our control; no delivery guarantee |

**Recommendation for the next authorized phase:** A or B as containment, C as the durable
boundary fix (it converts a platform artifact into a project-owned port, consistent with
BND-01/BND-03).

## 8. Control 1 — Decision Record (Post-Exit Control Resolution)

### 8.1 A diagnostic error, sustained for six recurrences

Recurrences #1–#6 all "fixed" the file by annotating the **outer** storage methods:

```ts
setItem: (key: string, value: string): Promise<void> => { ... }
```

`tsgo` kept reporting `TS7011` at columns 67 and 63 — positions that are **inside** the
statement, not at the method head. The actual unannotated function expression was the inner
callback:

```ts
return request(...).then(() => undefined);   //  <-- TS7011 reported here
```

So the recurrence was never purely platform drift. Part of it was **our repair repeatedly
missing the reported position** and then attributing the persistence to regeneration. The
ownership analysis in §1–§6 stands; the recurrence count was inflated by a misread diagnostic.
This is recorded rather than quietly corrected, because "we assumed the tool was wrong" is the
more valuable lesson than the annotation itself.

### 8.2 Resolution chosen

**Option A′** — a project-owned typecheck *contract*, combined with the now-correct annotation.

```text
Platform            Lovable Cloud integration scaffolder
Generated artifact  src/integrations/supabase/previewAuthStorage.ts
Ownership           content = platform · consumption + contract = Frontend Platform Owner
Canonical source    platform template (not in this repository)
Regen trigger       platform-side template revision / integration refresh
Project contract    scripts/audits/typecheck-app.mjs
```

`scripts/audits/typecheck-app.mjs` runs the **unchanged** strict typecheck and then classifies
each diagnostic as `PROJECT` or `PLATFORM` against a bounded, auditable allowlist
(file + error code + owner + finding + exception id). It:

- never relaxes `tsconfig.app.json`;
- never edits generated output;
- fails on **any** project-owned diagnostic;
- makes a future regeneration visible as a classified, non-blocking platform entry instead of an
  unexplained red gate.

Options B, C and D were not adopted: B duplicates typecheck projects, C is a real boundary
improvement but a Phase 1-scale change surface, D is outside our control.

### 8.3 Current evidence

```text
npx tsgo -p tsconfig.app.json --noEmit      exit 0   (0 diagnostics)
node scripts/audits/typecheck-app.mjs       exit 0   total=0 platform=0 project=0  verdict=PASS
```

The allowlist is currently **dormant** — it holds one entry that matches nothing today. That is
the intended steady state: it activates only if the platform regenerates the artifact without
the annotation, and it will then report the recurrence explicitly rather than blocking the gate.

### 8.4 Residual risk

Regeneration can still overwrite the file. The difference is that the outcome is now
**classified and owned** instead of rediscovered. Durable removal of the residual risk is
Option C (project-owned adapter port), deferred to Phase 1 under BND-01.
